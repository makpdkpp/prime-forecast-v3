01 / สรุปผลการตรวจ

ตรวจท้ายตามแผน Production PHP 8.4.27: ตัว PHP แก้ PHP2Shell หลักแล้ว แต่ยังค้าง Composer/MCP dependency advisories ผู้ใช้อนุญาต commit/push รายงานและเครื่องมือแล้ว โดยยังไม่อนุมัติ Production ดู หัวข้อ 13

เครื่องพัฒนานี้ยังใช้ PHP รุ่นที่ได้รับผลกระทบจาก PHP2Shell และยังไม่ควรถือว่าผ่านเกณฑ์สำหรับเปิดรับทราฟฟิกที่ไม่น่าเชื่อถือ

Critical · ยืนยันรุ่นที่ได้รับผลกระทบในเครื่องนี้

CLI เป็น PHP 8.3.30; Apache ถูกตั้งให้โหลดรุ่นเดียวกันด้วย mod_php และ GET /login ภายในเครื่องตอบ 200 พร้อม header PHP/8.3.30 สอดคล้องกับ config รุ่นแก้ไขขั้นต่ำบนสาขา 8.3 คือ 8.3.36 ต้องอัปเดตรันไทม์และเริ่ม worker ใหม่ ไม่ใช่แก้ Laravel อย่างเดียว [R1–R3]

จำนวน findings คือการจัดกลุ่มประเด็นที่ต้องดำเนินการ ไม่ใช่จำนวน CVE ทั้งหมด; ผล tests ผ่านไม่รับรองว่า PHP runtime ได้รับแพตช์ และไม่มีการทดลอง RCE / OOM / payload อันตราย

04 / ประเด็นที่ต้องดำเนินการ

P2S-01 · RUNTIME · LOCAL CONFIRMED

PHP ที่ใช้งานในเครื่องยังต่ำกว่ารุ่นแก้ PHP2Shell Critical

หลักฐาน
php -v = 8.3.30; mod_php.conf โหลด DLL รุ่นเดียวกัน; localhost GET /login ตอบ PHP/8.3.30 ขณะที่แพตช์สาขา 8.3 เริ่มที่ 8.3.36 [R1–R3]
ผลกระทบและเงื่อนไข
PHP รุ่นนี้อยู่ใน affected range ของสอง CVE เสี่ยง RCE ตามเงื่อนไขของ runtime และ request flow; หลักฐานนี้ยืนยันรุ่นที่ได้รับผลกระทบ ไม่ใช่ยืนยันว่าเครื่องถูกโจมตีหรือว่า exploit สำเร็จ การเปิดรับ request จากผู้ไม่เชื่อถือทำให้มีความเสี่ยงเร่งด่วน
แนวทางแก้
อัปเดต PHP web handler, CLI, queue และ scheduler ทุกตัว สำหรับ baseline โปรเจกต์ใช้ PHP 8.4.27 ขึ้นไปบน 8.4 หรือแพ็กเกจที่มีแพตช์ใหม่กว่า; หากคงสาขา 8.3 ต้องอย่างน้อย 8.3.36 หากใช้ Windows ให้เลือก build ที่รวม dependency fixes ล่าสุด (มี rebuild -1 เมื่อ 26 ต.ค.) แล้ว restart Apache / PHP workers [R1,R7]
เกณฑ์ปิดประเด็น
มีหลักฐานเวอร์ชัน/แพ็กเกจและ effective values ของทุก web worker / CLI ที่ใช้งานจริง พร้อม smoke tests หลัง restart; Linux ที่ใช้ backport ต้องมีหลักฐาน patch จาก vendor ไม่พิจารณาเลขเวอร์ชันต้นทางอย่างเดียว
P2S-02 · STARTUP CONFIGURATION · LOCAL CONFIRMED / FPM CONDITIONAL

.user.ini อย่างเดียวไม่ใช่หลักฐานว่า mitigation ทำงานก่อน request startup High

หลักฐาน
public/.user.ini:4 ตั้ง upload progress เป็น 0 แต่ local mod_php ไม่อ่านไฟล์นี้ และ raw CLI อ่านค่าเป็น 1; คู่มือ docs/php-production-security.md:29–33 ระบุเป็น fallback สำหรับ CGI/FastCGI โดยต้องเน้นข้อจำกัดเรื่อง initialization ให้ชัดเจนเพิ่ม [R2,R4]
ผลกระทบและเงื่อนไข
ผู้ deploy อาจเข้าใจว่าใส่ไฟล์นี้แล้วลด early session path ได้แล้ว สำหรับ FPM advisory ระบุ .user.ini ถูกใช้หลัง normal initialization จึงไม่ควรอาศัยไฟล์นี้เป็นมาตรการเพียงอย่างเดียวต่อ consumer ก่อน initialization การปิด upload progress ลดเส้นทางหนึ่ง แต่ไม่แก้ CVE ทั้งหมด
แนวทางแก้
ตั้ง session.upload_progress.enabled=0 ใน php.ini / server startup / FPM pool ที่ผู้ให้บริการยืนยันว่ามีผลทันเวลา; restart worker ทุกตัว เก็บ .user.ini เป็น defense in depth และตรวจทั้งค่า Master/Local ใน authenticated server view ไม่ใช้ ini_set ใน controller หรือสร้าง public phpinfo
เกณฑ์ปิดประเด็น
ได้หลักฐาน configuration ต้นทางที่โหลดก่อน parsing พร้อม effective web value = Off และ patched runtime; การอ่านไฟล์ .user.ini หรือ unit test ผ่านไม่เพียงพอ

09 / ข้อจำกัดและสิ่งที่ยังยืนยันไม่ได้

  • ไม่มี production/Plesk access หรือ web effective ini ที่เชื่อถือได้ของ production; HTTP header ภายในเครื่องเป็นเพียงหลักฐานประกอบ config ไม่แทนรายการโมดูล/Local Values ทุกตัว
  • ไม่ได้ยิง exploit, request ที่จงใจทำ OOM, session poisoning, web shell หรือ outbound SSRF; ไม่ได้อ้างว่า exploit สำเร็จ
  • ไม่ได้ตรวจ OS persistence, process memory, system-wide temp/session/cron หรือ server logs ภายนอกโปรเจกต์; การอ่าน process inventory ผ่าน CIM ถูกจำกัดสิทธิ์ ใช้ static Apache includes และ benign HTTP แทน
  • Token/regex scan ช่วยคัดกรอง candidate แต่ไม่พิสูจน์การไม่มีช่องโหว่ อาจไม่ครอบคลุม dynamic calls, obfuscation, malicious binaries, dependency tampering หรือ remote services; ไม่ได้ตรวจทุกบรรทัดของ third-party libraries ด้วยมือ
  • ไม่ได้แก้ source application, lockfile, .env, php.ini หรือ Apache config; ไฟล์ที่เพิ่มคือรายงานและหลักฐาน ผลทดสอบจำกัดอยู่ใน isolated environment ที่ระบุ
  • ไม่ใช้รายงานนี้ยืนยันว่าเคยหรือไม่เคยถูกโจมตี; สถานะ advisory อาจเปลี่ยนหลังวันที่ตรวจ จึงควรทวน official PHP/vendor advisories ก่อน deploy
